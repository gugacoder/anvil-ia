### Session (20:45) - Auditoria de arquitetura: Processa OS Fed

**Context:** Guga pediu confirmação sobre a arquitetura do `workspace/processa-os-fed/` — se usa iframe, como é a integração React, e quão robusta é a troca de state entre host (Shell) e apps federados.

**Decisions Made:**
- Nenhuma decisão nova — sessão puramente investigativa.

**Lessons Learned:**
- `processa-os-fed` usa **Module Federation puro** via `@originjs/vite-plugin-federation` v1.4.1 (Vite, não webpack). **Zero iframe.**
- Shell (host) carrega remotes (`chat`, `notas`) via `React.lazy(() => import("chat/App"))` — componentes React nativos no mesmo DOM.
- `react` e `react-dom` são `shared` na config de federation — instância única, sem duplicação de hooks/state.
- Auth compartilhada automaticamente: cookie httpOnly `so_session` (JWT) funciona cross-app porque tudo roda same-origin sob `/so/`.
- **Contextos do Shell (theme, windows, notifications) NÃO são acessíveis pelos remotes.** Cada remote gerencia seu próprio state interno.
- Comunicação host↔remote é **indireta**: passa pelo backend (REST API) ou por convenções CSS (classe `dark`/`light` no `<body>` + Tailwind `dark:`).
- CSS de remotes precisa de injeção manual (`useRemoteStylesheet` cria `<link>` no head) porque o plugin de federation não carrega CSS automaticamente.
- Error boundaries isolam crashes de remotes sem derrubar o Shell.
- Em dev: Shell (5631) faz proxy para Chat (5632), Notas (5633) e Server (5630). Em prod: servidor Hono único serve tudo.

**Takeaway arquitetural:** A integração é robusta no sentido de isolamento e auth, mas **não há state reativo compartilhado** entre host e remotes (sem context sharing direto). Se precisar disso no futuro, será necessário criar um mecanismo explícito (shared context via federation, custom events, ou store compartilhado).
