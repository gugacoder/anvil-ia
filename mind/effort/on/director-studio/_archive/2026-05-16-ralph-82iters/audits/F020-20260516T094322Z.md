# Veredito geral

**PASSA com 9 divergências conscientes** (todas documentadas no UX spec [[toaster]] §Divergências e/ou no cabeçalho do componente) e nenhuma falha de fidelidade contratual. Esta wave é, deliberadamente, **mudança de stack**: lib própria vendorizada `rnc__*` → **sonner**. O contrato N1..N12 é majoritariamente reinterpretado como divergência consciente positiva — o legado tem bugs e ausências (gate quebrado N11, sem dismiss N12, único-em-tela N9, sem stack N10, sem ARIA, sem action button, sem promise) que o Studio corrige intencionalmente. A fachada `useToast()` preserva a forma do hook (verbos por severidade + `(message, options?)`) garantindo migração ergonômica das ~25 call-sites do legado.

O smoke `/smoke-f020` cobre as 4 severidades (com durações diferenciadas), description, action, promise, duration Infinity e disparo em sequência (stack real visível). `dismiss()` global é exposto via botão dedicado. Routing TanStack monta `<Toaster />` na root do `main.tsx`, fora do `<Outlet />` (toast sobrevive a route change, edge case do UX spec).

# N1..N12

## N1 — 4 verbos, sem `error` (legado: info/success/danger/warning)

**FERE (divergência consciente — renomeação `danger → error`).** Contrato: `useNotifications()` retorna `{info, success, danger, warning}` (`useNotifications.js:69`). Studio: `useToast()` retorna `{success, info, warning, error, dismiss}` (`use-toast.ts:40-47`). O verbo de erro é **`error`**, alinhado a API moderna (sonner, react-hot-toast, etc). UX spec documenta explicitamente (linha 76, tabela de divergências, primeira linha: `danger → error`). Cabeçalho do hook não menciona o rename, mas o UX spec é canônico — recomendo aditar 1 linha no header do `use-toast.ts` apontando `// renomeacao consciente: danger (legado) -> error (Studio); ver [[toaster]] §Divergências`. **OK — divergência consciente declarada no UX spec; pass-with-note.**

## N2 — Default duration 5000 ms para todos os 4 tipos

**FERE (divergência consciente — durações diferenciadas).** Contrato: hook hardcode `dismiss.duration: 5000` para os 4 verbos (`useNotifications.js:32`). Studio: `DURATION = {success:4000, info:5000, warning:6000, error:8000}` (`use-toast.ts:30-35`). UX spec §Motion (linha 120-127) justifica: success some rápido, error fica mais tempo para reflexão. Smoke route mostra os números no header ("4s/5s/6s/8s"). Cabeçalho do hook documenta a tabela completa (linhas 16-17). **OK — divergência consciente, declarada em hook + UX spec + smoke.**

## N3 — Posicionamento top-center desktop, mobile-top em viewport ≤ 768

**FERE (divergência consciente — top-right desktop).** Contrato: `container: 'top-center'` fixo desktop, `mobile-top` (full-width 20px margens) em mobile (`useNotifications.js:33`, `Container.js:125-180`, `notifications.css:1-82`). Studio: desktop **`top-right`**, mobile **`top-center`** (`sonner.tsx:60-64` via `useIsMobile()`). UX spec §Posicionamento e Responsivo (linhas 137-143) é canônico: top-right é "padrão moderno", thumb-zone mobile preservada (top evita conflito com gestos rodapé). Cabeçalho do componente declara (linha 11). **OK — divergência consciente, justificada.**

## N4 — Não há "banner persistente" inline

**PASSA (fora de escopo declarado).** Contrato: legado não distingue banner; classes `top-full`/`bottom-full` produzem toast full-width flutuante, não banner ancorado. Studio: UX spec explicitamente **exclui** banner do Toaster (linha 39: "Banner persistente ancorado em página → [[inline-alert]] ou futuro `page-banner`"; linha 86: tabela "Banner full-width → Fora do escopo do Toaster — banner é spec separada"). Implementação `sonner.tsx` não tenta replicar `top-full`. **OK — decisão arquitetural correta: o que o legado chama de banner ou é toast comum ou é inline-alert; Studio separa as responsabilidades.**

## N5 — `pauseOnHover` opt-in no componente, forçado no hook

**PASSA.** Contrato: hook força `dismiss.pauseOnHover: true` (`useNotifications.js:32`). Studio: sonner pausa no hover **por default** (sem precisar prop) — cabeçalho do hook declara "hover pausa o timer automaticamente (sonner default)" (linha 23). Comportamento observável idêntico ao legado: passar mouse pausa, retirar retoma. UX spec §Estados (linha 110) e §Motion (linha 131) consolidam. **OK — semântica preservada via mecanismo nativo do sonner.**

## N6 — Barra de progresso `onScreen:true` visível em todos os toasts

**FERE (divergência cosmética consciente).** Contrato: hook força `dismiss.onScreen: true`, barra branca no fundo da cor (`useNotifications.js:32`, `Notification.js:262-292`). Studio: sonner **não renderiza barra de progresso visível por padrão**, e o `sonner.tsx` não opta-in. UX spec §Motion linha 131: "Hover (desktop): timer pausa imediatamente; visualmente, nenhuma alteração — o pause é silencioso (sem barra de progresso piscando)" — decisão consciente de **suprimir** a barra. Linha 80 da tabela §Divergências não menciona explicitamente a barra (apenas posição/stack/lib), porém o §Motion linha 131 carrega a decisão. **OK — divergência consciente; recomendo Curator aditar 1 linha em §Divergências do UX spec: `Barra de progresso | Sempre visível | Suprimida (decisão UX, sonner default)`.** pass-with-note (gap menor no UX spec).

## N7 — Dismiss por click no corpo, `showIcon:false` (sem X visível)

**FERE (divergência consciente — closeButton off, sem dismiss por click no corpo).** Contrato: legado tem dismiss por click em qualquer ponto do item (`dismiss.click:true` default), sem X visível (`showIcon:false`). Studio: `closeButton={false}` (`sonner.tsx:71`); sonner por padrão **não fecha por click no corpo** (default dismiss apenas no swipe mobile, action, ou timeout). UX spec §Estrutura visual (linha 96-97) mostra `[×?]` opcional e linha 156 documenta `<Toaster closeButton />` como override admin. Smoke route não testa click no corpo (testa só action e dismiss explícito). **OK — divergência consciente, UX moderna evita closes acidentais.** pass-with-note: edge case do UX spec linha 189 ("Toast com `Infinity` duration… ativar `closeButton` automaticamente") **não está implementado** — a função `fireInfinity` na smoke depende de `action` para fechar, e funciona, mas se o consumidor passar `duration:Infinity` sem `action` o toast fica permanentemente preso. Recomendo Smith adicionar guard no `useToast`: se `duration === Infinity && !options.action` → forçar `closeButton:true` no toast. **Não-bloqueante; nota para retrabalho.**

## N8 — Swipe-to-dismiss mobile, threshold 40% largura

**PASSA.** Contrato: handlers de touch ligados, `hasFullySwiped` exige ≥40% (`utils.js:367-371`). Studio: sonner implementa swipe nativo. UX spec §Motion linha 132: "Swipe-to-dismiss (mobile): arrastar horizontalmente. Threshold ~50% da largura. Animação acompanha o dedo". Threshold 50% vs 40% legado — diferença cosmética dentro do mesmo modelo mental, sem impacto observável significativo. Smoke não testa diretamente (precisa ambiente touch). **OK.**

## N9 — Único-em-tela do mesmo tipo, sem fila

**FERE (divergência consciente positiva — stack real).** Contrato: hook varre DOM antes de cada dispatch e suprime silenciosamente se já há toast do mesmo tipo na tela (`useNotifications.js:29-67`). Studio: `visibleToasts={3}` (`sonner.tsx:69`); múltiplos toasts coexistem; o 4º entra como fila e aparece quando um dos visíveis sai. Smoke F020 botão "disparar 5 (stack)" dispara 5 `info` em 80ms cada — comprova stack real. UX spec §Divergências linha 79 (Stack: legado suprime/Studio stack real) e §Edge cases linha 188 ("Não suprimir como o legado fazia (decisão consciente)"). **OK — corrigindo má-prática legada.**

## N10 — Toda chamada faz `removeAllNotifications` antes, com janela de 500ms

**FERE (divergência consciente positiva — sem clear destrutivo).** Contrato: cada `notify()` chama síncrono `Store.removeAllNotifications()` e dispara o novo 500ms depois — "novo sempre vence anterior" com janela vazia visível. Studio: cada dispatch é aditivo no stack do sonner; não há clear automático. O clear global existe **como opção explícita** (`t.dismiss()` sem id) — smoke "dismiss() todos". UX spec §Edge cases linha 187: "Dois toasts disparados em sucessão rápida (< 200ms): sonner stackeia naturalmente". **OK — comportamento moderno, controle explícito ao consumidor.**

## N11 — Gate do `getElementsByClassName` está bugado (classe não bate)

**PASSA (bug não reproduzido por design).** Contrato: gate de unicidade do hook usa selector `notification__item notification__item--<type>` mas o componente renderiza `rnc__notification-item rnc__notification-item--<type>` — gate sempre passa, bug positivo. Studio: nenhum gate baseado em selector de DOM; dedup é responsabilidade do consumidor (UX spec §Edge cases linha 192: "Erro de rede recorrente… considerar deduplicar por `id` no caller (não no Toaster)"). Mecanismo equivalente: passar `id` estável no `options` faz sonner substituir in-place (UX spec linha 62 da tabela, `id`: "Disparo com mesmo `id` substitui o anterior in-place"). Smoke `firePromise` exercita via `toast.promise` (mesmo slot loading→success/error). **OK — bug eliminado por design + via melhor de dedup disponível.**

## N12 — Sem dismiss programático (componentes só sabem disparar)

**FERE (divergência consciente positiva — `dismiss(id?)` exposto).** Contrato: hook retorna apenas `{info, success, danger, warning}`, sem dismiss. Studio: `useToast()` expõe `dismiss(id?)` (`use-toast.ts:46, 59`) — sem id fecha todos, com id fecha um específico. Smoke F020 seção "Controle global" tem botão `t.dismiss()` que fecha tudo. UX spec §Divergências linha 80 ("Dismiss programático | Inexistente | `dismiss(id?)` disponível"). **OK — API moderna, divergência mandatada.**

# Pontos a revisitar fora desta auditoria

1. **N6 (barra de progresso)** — UX spec §Divergências não tem linha explícita sobre supressão da barra de progresso. §Motion linha 131 implica a decisão ("o pause é silencioso, sem barra de progresso piscando"), mas a tabela canônica de divergências ignora. **Solicitar ao Curator aditar 1 linha**: `Barra de progresso | Sempre visível (onScreen:true forçado) | Suprimida (sonner default)`.
2. **N7 (Infinity + closeButton)** — Edge case do UX spec linha 189: "se `duration === Infinity`, ativar `closeButton` automaticamente (override do default)". **Não implementado** no `use-toast.ts`. Smoke `fireInfinity` driblou usando `action: {label:"Fechar"}` (que fecha o toast ao clicar), mas se um caller usar `duration:Infinity` sem action o toast trava. **Recomendar Smith**: no `useToast`, detectar `options?.duration === Infinity` e injetar override `{closeButton:true}` (sonner aceita `closeButton` por toast nas options, via `dismissible`/passe pelo Toaster prop ou usar `action` obrigatório). Ou documentar no header do hook que `Infinity` exige `action`. Não-bloqueante para F020.
3. **N1 (rename) no header do hook** — Cabeçalho do `use-toast.ts` (linhas 1-25) documenta API e durações mas **não menciona** o rename `danger → error` nem aponta para o UX spec / contrato legado. Recomendo aditar 1-2 linhas em "Decisoes da spec": `// - Verbo de erro: 'error' (legado: 'danger'); rename consciente, ver [[toaster]] §Divergências.`
4. **`onDismiss` / `onAutoClose`** — UX spec §API linha 64-65 documenta esses callbacks como parte da API conceitual. Implementação: `ExternalToast` do sonner já suporta nativamente (passa pelo spread `...options` em `use-toast.ts:52-58`). **OK por inércia**, mas não há smoke cobrindo — adicionar à wave de testes integrados quando F020 sair de smoke para feature exercitada por real.
5. **A11y observada** — sonner aplica `role=status`/`role=alert` por severidade (UX spec §Acessibilidade linha 147-149). Não auditei DOM renderizado para confirmar mapeamento `info/success → status`, `warning/error → alert`. **Solicitar UI-tester** verificar em runtime.
6. **`maxQueryLength` / verbo extra `loading`** — `sonner.tsx:40-45` define ícone para `loading` (`CircleNotch` animado), e `toast.promise` exercita via smoke `firePromise`. `useToast` **não expõe** verbo `loading` direto (só `success/info/warning/error/dismiss`). Caller que quiser `loading` precisa usar `toast.loading(...)` da API funcional (re-exportada em `sonner.tsx:108`). **OK** — é caminho documentado, mas se Curator quiser uniformidade pode aditar `loading` no hook.
7. **Sem nota sobre lib base no header do componente** — `sonner.tsx:3-18` documenta decisões mas não diz "sonner v?.?.?". Considerar adicionar versão para rastreabilidade futura.
